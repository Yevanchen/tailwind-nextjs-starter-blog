我们可以承认最早的 script 来自于 mastra 的 workflow ，我们可以用自然语言表达工具调用然后用 function calling 实现它或者说用一个更直接专业的表达：“工具链编排” - 实现 Claude 无法完成的多步自动化 (The "Tool Chaining" Experience) ，但是后来我发现我在 cursor 里做很多事情 但是左侧的代码驾驶舱似乎对我来说没那么重要，但是 den 的出现让我发现或许我们应该设计成那样

script 太通用了，它的功能的可发现性太差，世界上也无数的人尝试在构建输入框的时候告诉人们可以做什么

在工程师使用 cursor 的时候 我们可以说代码的结果才是交付物，但是对于工程师的暂时的工作而言 他其实只关心代码本身，对于 notion 也是一样的道理文本是交付物所以才需要这么大的布局 但是 script 并不是这样的 script 的交付物是对现实世界的影响 人们真的喜欢在侧边栏里输入吗

另外对于左边的文件系统其实真的很容易将他和记忆联想在一起不过这只是表层，但是目前的不对劲是生成的结果只是文档或者是其他任务的 context

左边的文件系统现在的构成 = 生成的文档+可以运行的 script+别人的文档

然后对于 supervisor 和 script 的关系就很像 我写一个邮件 request 大堂经理或者我只是当面和他简单聊聊

最终我觉得当我想输入什么的时候我不知道到底应该在 script 本体内写还是直接写给 supervisor我的需求到底是写在左边还是右边

什么是上下文工程最好最符合直觉的交互，我们到底要解决什么问题？
